# PostgreSQL 分库分表架构设计方案

## 一、架构概述

### 1.1 分库策略

根据业务特点,将数据库拆分为5个库:

1. **bx_core** - 核心业务库
   - 用户信息、系统配置、权限管理
   - 读写频繁,需要高可用

2. **bx_finance** - 财务库
   - 充值、提现记录
   - 强一致性要求,需要事务支持

3. **bx_log** - 日志库
   - 钱包流水、收益记录
   - 写入量大,需要分表

4. **bx_marketing** - 营销库
   - 红包、抽奖、优惠券
   - 读写分离优化

5. **bx_trade** - 交易库
   - 产品订单
   - 按时间分表,支持历史数据归档

### 1.2 分表策略

**注意**: 分表功能由应用层框架实现（如ShardingSphere、Citus等），数据库层面只创建单表结构。

#### 推荐的分表方案（由应用框架实现）

| 表名 | 推荐分表方式 | 推荐分表数 | 分表键 | 说明 |
|------|---------|--------|--------|------|
| wallet_log | 按用户ID哈希 | 16-32 | uid | 钱包流水表,写入量大 |
| pro_reward | 按用户ID哈希 | 16-32 | uid | 收益记录 |
| fin_paylog | 按月份 | 动态 | create_time | 充值记录 |
| fin_cashlog | 按月份 | 动态 | create_time | 提现记录 |
| pro_order | 按月份 | 动态 | create_time | 订单记录 |
| sys_log | 按日期 | 动态 | create_time | 系统日志 |

### 1.3 读写分离

- **主库**: 处理所有写操作和实时性要求高的读操作
- **从库1**: 处理管理端统计查询
- **从库2**: 处理用户端查询(如团队数据、收益历史等)

## 二、性能优化策略

### 2.1 索引优化

```sql
-- 复合索引优化查询
CREATE INDEX idx_user_status_gid ON sys_user(status, gid) WHERE status < 99;
CREATE INDEX idx_paylog_uid_status_day ON fin_paylog(uid, status, create_day);
CREATE INDEX idx_order_uid_status_day ON pro_order(uid, status, create_day);
CREATE INDEX idx_reward_uid_type_time ON pro_reward(uid, type, create_time);
```

### 2.2 分表实现（应用层框架负责）

数据库层面创建单表，分表由应用层框架实现：
- **ShardingSphere**: 支持分库分表、读写分离
- **Citus**: PostgreSQL分布式扩展
- **自定义路由**: PHP应用层实现路由逻辑

```sql
-- 数据库只创建单表结构
CREATE TABLE fin_paylog (
    id SERIAL PRIMARY KEY,
    uid INTEGER NOT NULL,
    money NUMERIC(16,2),
    create_time INTEGER,
    create_day INTEGER,
    -- 其他字段...
);

-- 索引优化
CREATE INDEX idx_paylog_uid ON fin_paylog(uid);
CREATE INDEX idx_paylog_day ON fin_paylog(create_day);
```

### 2.3 物化视图

为管理端统计创建物化视图,减少实时计算压力:

```sql
-- 用户统计物化视图
CREATE MATERIALIZED VIEW mv_user_statistics AS
SELECT 
    u.id,
    u.account,
    u.total_invest,
    u.total_invest2,
    COALESCE(p.total_money, 0) as total_recharge,
    COALESCE(c.total_money, 0) as total_withdraw,
    COALESCE(r.total_reward, 0) as total_reward
FROM sys_user u
LEFT JOIN (SELECT uid, SUM(money) as total_money FROM fin_paylog WHERE status=9 GROUP BY uid) p ON u.id = p.uid
LEFT JOIN (SELECT uid, SUM(money) as total_money FROM fin_cashlog WHERE status=9 GROUP BY uid) c ON u.id = c.uid
LEFT JOIN (SELECT uid, SUM(money) as total_reward FROM pro_reward GROUP BY uid) r ON u.id = r.uid
WHERE u.status < 99;

-- 创建索引
CREATE UNIQUE INDEX ON mv_user_statistics(id);

-- 定时刷新(每5分钟)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_user_statistics;
```

## 三、数据迁移策略

### 3.1 迁移步骤

1. **第一阶段**: 创建PostgreSQL数据库和表结构
2. **第二阶段**: 历史数据迁移(离线,可以停机或双写)
3. **第三阶段**: 增量数据同步(使用binlog或应用层双写)
4. **第四阶段**: 灰度切换(先切读,再切写)
5. **第五阶段**: 完全切换,下线MySQL

### 3.2 数据一致性保证

- 使用事务确保数据完整性
- 关键操作添加分布式锁
- 重要表添加版本号字段,支持乐观锁

## 四、分库分表路由规则

### 4.1 用户维度路由

```php
/**
 * 根据用户ID计算分表后缀
 */
function getTableSuffix($uid, $tableCount = 16) {
    return $uid % $tableCount;
}

/**
 * 获取钱包流水表名
 */
function getWalletLogTable($uid) {
    $suffix = getTableSuffix($uid, 16);
    return "wallet_log_" . $suffix;
}
```

### 4.2 时间维度路由

```php
/**
 * 根据时间获取分表名
 */
function getTimeBasedTable($baseTable, $time, $partitionType = 'month') {
    if ($partitionType === 'month') {
        return $baseTable . '_' . date('Ym', $time);
    } elseif ($partitionType === 'day') {
        return $baseTable . '_' . date('Ymd', $time);
    }
    return $baseTable;
}

/**
 * 获取充值记录表名
 */
function getPaylogTable($createTime) {
    return getTimeBasedTable('fin_paylog', $createTime, 'month');
}
```

## 八、业务适配建议

### 8.1 代码改造点

1. **数据库连接管理**: 支持多数据源
2. **SQL改写**: 跨库关联查询改为应用层聚合
3. **事务处理**: 分布式事务使用两阶段提交或最终一致性
4. **缓存策略**: Redis缓存热点数据

### 8.2 查询优化

```php
// 不推荐: 跨库JOIN
SELECT u.*, SUM(o.money) 
FROM bx_core.sys_user u 
JOIN bx_trade.pro_order o ON u.id = o.uid;

// 推荐: 应用层聚合
$user = Db::connect('bx_core')->table('sys_user')->find($uid);
$orderSum = Db::connect('bx_trade')->table('pro_order')
    ->where('uid', $uid)->sum('money');
```

## 九、预期性能提升

- **查询性能**: 提升 60%-80% (通过分表和索引优化)
- **写入性能**: 提升 50%-70% (通过分库分表降低锁竞争)
- **并发能力**: 支持 10000+ QPS (通过读写分离)
- **存储成本**: 降低 30% (PostgreSQL压缩率更高)

## 十、风险与应对

### 10.1 潜在风险

1. **数据不一致**: 迁移过程中可能出现数据丢失
2. **性能下降**: 分库分表初期可能性能不稳定
3. **业务中断**: 切换过程可能影响业务

### 10.2 应对措施

1. 完整的备份恢复方案
2. 灰度发布,逐步切换
3. 准备回滚方案
4. 充分的压力测试
